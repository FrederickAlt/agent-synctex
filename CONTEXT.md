# Context

This repository implements TeX Actions: a stdio MCP server for compiling LaTeX, opening PDFs in a Host-served PDF.js/LaTeX-Workshop viewer, and performing forward/reverse SyncTeX navigation.

The important architecture goal is a clean split between:

- the **MCP runtime** that exposes tools to agents;
- the **Viewer Host Client** inside the MCP runtime that owns MCP-side `pdf_id` state and sends typed messages;
- the **Viewer Host Server** that serves the browser viewer, PDF bytes, sockets, registration, refresh routing, lease-backed in-memory pending marks, and server-side SyncTeX hover/probe responses;
- the **direct browser viewer** that owns visible tabs, PDF.js interaction, browser coordinate conversion, overlays, scrolling, and user interaction;
- the **SyncTeX resolution** module that owns parsing/scoring/source repair/result shaping on the Node side.

There is one active viewer architecture: Viewer Host Client, Viewer Host Server, and the direct `viewer_lw` PDF.js browser viewer. The former standalone `/app` iframe shell has been removed.

## Composition root and active entrypoints

The installed package has two active production entrypoints:

- Installed CLI and MCP composition root: `scripts/agent-synctex.ts`
  - dispatch implementation: `src/modules/installer/cli.ts`
  - `agent-synctex mcp` starts `src/modules/stdio_mcp_runtime.ts`
  - `agent-synctex fetch-info` retrieves hook-injected PDF context through `src/modules/hook_context.ts`
  - install, uninstall, and doctor commands use the harness adapters under `src/modules/installer/`
- Viewer Host process entrypoint: `scripts/viewer-host-server.ts`
  - server implementation: `src/modules/viewer_host_server.ts`

`test/viewer_guardrails.test.ts` and `scripts/build-package.ts` track these production entrypoints. Two additional source-tree scripts are not included in the installed package build:

- `scripts/tex-actions-mcp.ts` — direct source-tree stdio MCP convenience entrypoint;
- `scripts/pdf-preview-mcp.ts` — compatibility shim that imports `scripts/tex-actions-mcp.ts`.

Important runtime composition modules:

- Stdio runtime and per-agent bundle: `src/modules/stdio_mcp_runtime.ts`
- MCP tool parser/handler and schemas: `src/modules/host_service_mcp.ts`
- MCP stdio framing: `src/modules/mcp_stdio_transport.ts`
- Viewer Host Client / MCP-owned PDF state: `src/modules/viewer_host_client.ts`
- Viewer Host control and marks HTTP clients: `src/modules/viewer_host_control_client.ts`, `src/modules/viewer_host_marks_client.ts`
- Viewer Host protocol types and validators: `src/modules/viewer_host_protocol.ts`
- Viewer Host discovery/state-file ownership: `src/modules/viewer_host_discovery.ts`
- Viewer Host PDF registry: `src/modules/viewer_host_registry.ts`
- Lease-backed pending PDF marks: `src/modules/pending_pdf_marks.ts`
- Bounded transient Host event backlog: `src/modules/viewer_host_event_backlog.ts`
- Harness hook mark retrieval: `src/modules/hook_context.ts`

There is no packaged native Pi extension entrypoint in production. Harness integration is installed through MCP configuration plus hook/plugin wrappers generated by `src/modules/installer/`. Pi installation is implemented by `src/modules/installer/adapters/pi.ts`, which writes the wrapper produced by `src/modules/installer/pi_extension_source.ts`. `src/modules/pi_adapter/pi_adapter.ts` is currently an unwired generic Pi tool-registration helper, not an active integration path.

`src/modules/stdio_mcp_runtime.ts` creates the default `ViewerHostMcpService` unless tests inject custom `pdfOperations`. That service is the active viewer integration path for `open_pdf`, `jump_pdf`, `show_latex`, and `compile_latex_file(open_pdf=true)`.

One stdio MCP process binds to one agent identity. Stateless protocol calls such as initialization and `tools/list` do not create agent state; the first stateful tool call binds the runtime, and later calls that claim a different agent identity are rejected. The resulting runtime bundle owns one compile service and one Viewer Host MCP service, which lazily launches or reuses at most one Viewer Host process. Hooks read that agent's `viewer-host.json` and call the same Host's mark endpoints; they do not start a second bridge server.

## MCP tool surface

MCP tool protocol, validation, workspace-context parsing, and user-facing result formatting live in:

- `src/modules/host_service_mcp.ts`

The exported MCP tools are:

- `show_latex`
- `compile_latex_file`
- `open_pdf`
- `jump_pdf`
- `fetch_pdf_context` (manual/no-hooks mode only; hidden in hook-capable harness mode)

Tool handlers delegate PDF operations through the `HostServiceMcpPdfOperations` interface in `src/modules/host_service_mcp.ts`. In normal stdio runtime, those operations come from `ViewerHostMcpService.pdfOperations` in `src/modules/viewer_host_client.ts`.

Important MCP invariants:

- `workspace_context` is injected by `src/modules/stdio_mcp_runtime.ts` for stdio callers.
- `open_pdf` and compile-open flows return a process-local `pdf_id`.
- `jump_pdf` requires a known active `pdf_id` and a readable source file, or enough information to infer the default `.tex` source from the PDF path.
- `fetch_pdf_context` claims pending Viewer Host marks, formats only the marks that fit as source-cited context, and acknowledges exactly those rendered marks. Unrendered or failed claims remain available after lease release/expiry.

## LaTeX PDF production

LaTeX compile orchestration lives in:

- `src/modules/host_service_compile.ts`
- compile serialization and freshness caching in `src/modules/host_service_root_compile_coordinator.ts`
- compiler execution and diagnostics in `src/modules/latex/latex_file_compiler.ts`
- preamble parsing/discovery in `src/modules/latex/latex_preamble.ts` and `src/modules/latex/latex_preamble_index.ts`

`src/modules/runtime_preamble.ts` remains in the tree but has no active production caller; do not treat it as the current preamble integration path.

`show_latex` and `compile_latex_file` both use `HostServiceCompileService` from `src/modules/host_service_compile.ts`.

Compile behavior:

- Snippets are written to runtime files, compiled with SyncTeX enabled, and opened by default.
- File compilation can run compile-only or `open_pdf=true`.
- Compile-only calls mark an already tracked PDF as maybe updated through `pdfOperations.markTrackedPdfUpdated`.
- Compile-open calls open the resulting PDF through `pdfOperations.openPdf`, which in the active runtime is `ViewerHostMcpService.openPdf`.

## Viewer Host Client

The Viewer Host Client module is:

- `src/modules/viewer_host_client.ts`

Its main class is `ViewerHostMcpService`.

Responsibilities:

- allocate MCP-owned `pdf_id` values;
- keep process-local records mapping `pdf_id` to PDF path, workspace cwd, revision metadata, and viewer URL;
- launch/connect to a Viewer Host Server via `createDefaultViewerHostClientFactory`;
- send typed Viewer Host protocol messages over a `ViewerHostClient` adapter;
- recover from Viewer Host reconnects by re-registering known PDFs;
- implement `openPdf`, `jumpPdf`, `getPdfEvents`/`fetchPdfContext` internals, and `markTrackedPdfUpdated` for MCP handlers;
- store agent-readable PDF events in `PdfEventStore` from `src/modules/pdf_events.ts`.

Important concrete adapters/classes in `src/modules/viewer_host_client.ts`:

- `ViewerHostClient` — the interface used by `ViewerHostMcpService` to send Host messages.
- `FakeViewerHostClient` — test adapter that records messages.
- `HttpViewerHostProcessClient` — the HTTP adapter used for normal persistent Host communication and reuse.
- `LocalViewerHostProcessClient` — the owned-child adapter used for nonpersistent Host operation.
- `launchLocalViewerHostProcess` — launches the server process, validates its ready line, and returns the appropriate adapter.
- `SystemBrowserViewerLauncher` — opens/focuses the stable direct browser viewer entrypoint when the Host needs to be visible.

Important flows:

- `openPdf` validates the PDF path, allocates/reuses `pdf_id`, sends `open_pdf` or `focus_pdf` to the Host, and returns viewer metadata.
- `jumpPdf` resolves forward SyncTeX through `src/modules/synctex/synctex_resolution.ts`, then sends `synctex_forward` to the Host.
- `markTrackedPdfUpdated` sends `pdf_maybe_updated` to the Host so the Host can verify the file snapshot and broadcast refresh if needed.
- `getPdfEvents` asks the Host client to drain queued viewer events, maps reverse SyncTeX events through SyncTeX resolution, and returns agent-readable events.

## Viewer Host protocol

Typed Host protocol definitions and validators live in:

- `src/modules/viewer_host_protocol.ts`

The authenticated MCP control channel carries:

- `hello`
- `open_pdf`
- `focus_pdf`
- `set_debug_synctex`
- `synctex_forward`
- `pdf_maybe_updated`
- `clear_pdf_annotations`
- `compile_status`
- `report_error`
- `reverse_synctex_hover_result`

The browser viewer socket carries:

- `reverse_synctex`
- `pdf_annotation`
- `pdf_annotation_deleted`
- `reverse_synctex_hover`
- `compile_action`
- `selection_debug` only in explicit debug mode

Forward probe does not use either channel: the browser sends an authenticated `POST /synctex/probe`, and the Host returns `reverse_synctex_forward_probe_result` in the HTTP response.

Tab close is converted by the Host into a transient `viewer_tab_closed` event. Annotations use the separate `/marks/claim`, `/marks/ack`, and `/marks/release` lease protocol rather than the transient event drain.

The protocol is JSON-serializable. Keep it browser-friendly and avoid leaking Node objects into message payloads.

## Viewer Host Server

The Viewer Host Server module is:

- `src/modules/viewer_host_server.ts`

The standalone process entrypoint is:

- `scripts/viewer-host-server.ts`

The server binds locally by default and announces a ready line on stdout. `launchLocalViewerHostProcess` validates that line before opening/focusing the stable browser viewer URL. Persistent Host discovery is stored in the agent runtime directory by `src/modules/viewer_host_discovery.ts`. Reuse requires matching protocol and instance identity plus an authenticated control-channel hello; retirement uses the instance's authenticated shutdown endpoint rather than PID signalling.

Viewer Host Server responsibilities:

- listen on HTTP/WebSocket;
- expose authenticated `/control` for MCP-to-Host messages;
- serve `/viewer-lw` and `/viewer-lw/:pdf_id` as the direct tabbed viewer, plus vendored PDF.js/LaTeX-Workshop assets;
- redirect the compatibility route `/viewer/:pdf_id` to `/viewer-lw/:pdf_id`;
- serve `/config/:pdf_id.json` with PDF URL, revision, and viewer socket URL;
- serve `/pdf/:pdf_id?revision=N` with registered PDF bytes only when the requested revision matches the registered snapshot;
- expose `/viewer-events` SSE for open/focus tab events;
- expose `/viewer-tab-closed` and `/viewer-tab-selected` for direct-viewer tab notifications;
- expose authenticated `/marks/claim`, `/marks/ack`, and `/marks/release` for leased user-mark delivery;
- expose authenticated `/mcp-events/drain` for bounded transient non-mark events;
- expose token-authenticated `/synctex/probe` for browser forward-probe requests;
- expose token-authenticated `/heartbeat` and `/shutdown` for exact-instance lifecycle control;
- accept `/viewer-socket` WebSocket connections from the browser viewer;
- track connected viewer sockets per `pdf_id`;
- detect PDF file changes, debounce them, increment revisions, and broadcast `pdf_refresh`;
- compute low-latency hover/probe SyncTeX results through `src/modules/synctex/synctex_resolution.ts`.

Important separation rule: the Host Server serves and routes browser code but does not own user-facing PDF.js UI policy. Visible tabs and rendering behavior belong to `host_lw_adapter.mjs`. SyncTeX parsing/scoring belongs to SyncTeX resolution.

## Viewer Host access policy

The access/origin policy module is:

- `src/modules/viewer_host_access_policy.ts`

Its interface is `ViewerHostAccessPolicy`.

Responsibilities:

- decide bind host;
- construct browser-facing origin from server address;
- construct `/viewer-lw`, `/pdf`, and `/viewer-socket` URLs;
- decide whether a viewer WebSocket `Origin` header is allowed.

Current adapter:

- `LocalLoopbackViewerHostAccessPolicy`

It is intentionally loopback-only (`127.0.0.1`). If adding LAN/mobile support, add or extend an adapter at this seam instead of scattering host/origin/auth decisions through `ViewerHostServer` or the browser viewer.

Security note for future LAN/mobile mode: socket/probe tokens already exist per PDF and Host control/mark/event routes use a control token, but remote access would still need an explicit policy for `/viewer-lw`, `/config`, `/pdf`, `/viewer-events`, `/synctex/probe`, and browser tab-notification routes before exposing the server beyond loopback.

## Direct browser viewer

The browser viewer files are:

- `src/viewer_lw/viewer.html`
- `src/viewer_lw/host_lw_adapter.mjs`

They are served by `ViewerHostServer` at:

- `/viewer-lw`
- `/viewer-lw/:pdf_id`

Responsibilities:

- maintain visible PDF tabs;
- open/focus PDFs in the same PDF.js document viewer without an iframe app shell;
- close visible tabs without unregistering MCP-owned `pdf_id` state;
- listen to `/viewer-events` for `open_pdf` and `focus_pdf` messages;
- keep navigation history per PDF and route back/forward mouse/key shortcuts to the active PDF;
- reconcile active configuration after socket reconnects and ignore stale refresh/prefetch completions;
- bound and abort the prefetched-document cache so inactive documents cannot grow memory without limit.

The browser viewer is portable browser code. It must not import Node filesystem APIs or MCP internals.

## PDF.js / LaTeX-Workshop viewer route

The per-PDF viewer route is:

- `/viewer-lw/:pdf_id`

The Host serves the vendored viewer shell from:

- `src/viewer_lw/viewer.html`

The main Host-specific browser glue is:

- `src/viewer_lw/host_lw_adapter.mjs`

Vendored PDF.js/LaTeX-Workshop assets are under:

- `src/viewer_lw/`

`host_lw_adapter.mjs` responsibilities:

- fetch `/config/:pdf_id.json`;
- configure PDF.js options and default PDF URL;
- own direct-viewer tab state and inactive-document prefetching;
- connect to `viewer_socket_url`;
- convert browser click/selection geometry into PDF-space coordinates;
- send `reverse_synctex`, annotation, compile-action, and hover messages over the viewer socket, send forward probes through `POST /synctex/probe`, and send `selection_debug` only in explicit debug mode;
- handle `pdf_refresh` by reloading PDF bytes while preserving page/scale/scroll state;
- handle `synctex_forward` by rendering overlays and scrolling;
- render hover/probe overlays returned by the server;
- keep SyncTeX overlays aligned after resize, scale, and page render events;
- maintain viewer-local navigation history/back-forward behavior.

Important rule: `host_lw_adapter.mjs` may compute PDF coordinates and draw overlays, but it must not parse SyncTeX sidecars, score candidates, repair source locations, or choose source files/lines. That logic belongs in `src/modules/synctex/synctex_resolution.ts`.

## SyncTeX resolution

The deep SyncTeX resolution module is:

- `src/modules/synctex/synctex_resolution.ts`

It wraps lower-level SyncTeX and text-repair functionality from:

- `src/modules/synctex/forward_synctex.ts`
- `src/modules/synctex/latex_workshop/worker.ts`
- `src/modules/synctex/text_repair.ts`
- `src/modules/synctex/source_line.ts`
- `src/modules/synctex/source_index.ts`

Responsibilities:

- resolve forward SyncTeX jump requests into page/x/y/ranges/source diagnostics;
- resolve reverse SyncTeX viewer messages into `PdfEventStore` inputs;
- repair selection endpoints when selected text uniquely maps in source;
- inspect hover candidates and shape hover result messages;
- map reverse-click-to-forward-probe results and shape probe result messages;
- centralize SyncTeX parsing/scoring/source-repair payload shaping so MCP and Host paths do not duplicate it.

Callers:

- `ViewerHostMcpService.jumpPdf` in `src/modules/viewer_host_client.ts` uses `resolveForwardSynctexJump`.
- `ViewerHostMcpService` reverse-event handling uses `reverseSynctexPdfEventFromViewerMessage`.
- `ViewerHostServer` uses `reverseSynctexHoverResult` in its hover socket handler and `reverseSynctexForwardProbeResult` in its authenticated `/synctex/probe` HTTP handler.

## Viewer events and agent-readable PDF events

PDF event types and storage live in:

- `src/modules/pdf_events.ts`

`PdfEventStore` stores bounded process-local reverse SyncTeX, annotation, and debug events with monotonically increasing sequence numbers. It supports:

- filtering by `pdf_id`;
- hiding `selection_debug` events by default;
- returning only unread events unless `stale=true`.

Agent flow:

1. The viewer sends reverse/selection/annotation messages over its socket.
2. The Host stores annotations in `PendingPdfMarkStore`; it stores bounded transient control/debug events separately in `ViewerHostEventBacklog`.
3. Manual `fetch_pdf_context` and harness hooks use the same authenticated mark client to claim a lease, format a bounded response, acknowledge only rendered marks, and explicitly release the claim when delivery fails.
4. The Host broadcasts the exact acknowledged annotation IDs so browser state clears only consumed marks. Updated marks and unacknowledged claim members remain pending.
5. Reverse SyncTeX events drained by `ViewerHostMcpService.getPdfEvents` are resolved through SyncTeX resolution and stored in bounded `PdfEventStore` state. Debug events are stored directly; compile actions and tab-close events use dedicated handlers.

Normal viewer sessions do not enqueue selection-debug diagnostics. Those messages are enabled only for explicit `debug_synctex` sessions.

## End-to-end interaction flows

### Startup and tool dispatch

1. A configured harness starts `agent-synctex mcp`.
2. `src/modules/installer/cli.ts` starts `TexActionsStdioMcpRuntime`.
3. `McpStdioFrameLoop` serializes incoming requests.
4. The first stateful tool call binds the agent identity, injects workspace context, and creates one `HostServiceCompileService` plus one `ViewerHostMcpService`.
5. `src/modules/host_service_mcp.ts` validates and dispatches the tool call.

### Compile, open, and forward jump

1. `show_latex` or `compile_latex_file` calls `HostServiceCompileService`.
2. The compile service coordinates requests, invokes the LaTeX compiler helpers, and produces or updates the PDF and SyncTeX sidecar.
3. Open-enabled compile calls and `open_pdf` call `ViewerHostMcpService.openPdf`, which owns `pdf_id` allocation and registration.
4. `jump_pdf` resolves the source location through SyncTeX resolution before the client sends `synctex_forward` to the Host.
5. The Host updates its registry and routes open/focus/refresh/forward messages to the direct browser viewer.

### Reverse navigation and annotations

1. The browser sends reverse SyncTeX, annotation, hover, debug, and compile-action messages over its viewer socket.
2. The Host resolves hover immediately, stores annotations in `PendingPdfMarkStore`, and queues transient events in `ViewerHostEventBacklog`.
3. `ViewerHostMcpService` drains reverse/compile/debug events; reverse events are resolved and stored in `PdfEventStore`.
4. Hooks or manual `fetch_pdf_context` claim annotations, format bounded source-cited context, acknowledge rendered marks, and release failed claims.
5. The Host broadcasts acknowledged annotation IDs so the browser clears only consumed marks.

### Browser forward probe and viewer compile actions

- Forward probe is browser → authenticated `POST /synctex/probe` → Host SyncTeX resolution → HTTP result; it does not traverse the MCP runtime.
- Browser `compile_action` is queued by the Host, drained by `ViewerHostMcpService`, and handled by the compile-action controller in `src/modules/stdio_mcp_runtime.ts`. The controller runs a one-shot compile or manages continuous `latexmk`, then returns `compile_status` through the Host to the browser.
